What is this?

Think of it as a quality checklist for web products — not a color palette or font picker. It answers questions like:

  • What should a loading spinner look like vs. a skeleton screen?
  • How should checkout handle errors without losing the user's data?
  • What makes a button accessible to keyboard and screen reader users?
  • When is it OK to animate something — and when is it not?
Good to know: This is a written standard you can copy into your project and pin to a version. It's not a component library — you still build UI in your own stack (React, Vue, etc.).

Technically, it's a "Human Interface Guidelines (HIG) and product-engine contract." You don't need to remember that — just know it's the shared source of truth for how your web UI should behave.

Rules everyone follows

No matter what you're building, these always apply. If you're short on time, make sure your work passes this list:

  • Works on mobile — layout adapts; touch targets are big enough to tap
  • Keyboard accessible — you can tab through controls; focus is visible
  • Accessible to assistive tech — use real HTML elements (<button>, not <div onclick>); images have alt text
  • Handles real-world states — loading, empty, error, and success are designed — not afterthoughts
  • Uses design tokens — colors and spacing come from your token system, not random hex values
  • Respects reduced motion — animations aren't required to understand the UI
  • Fast enough — doesn't block the page with unnecessary JavaScript
  • Secure basics — no secrets in frontend code; sensitive data is masked
Want the full short list? HIG-LITE.md has every essential rule with links to the detailed spec. That's the best place to start reading.

How to read the docs

The full specification is large on purpose — but you don't read it all at once. The docs are split so you only open what you need:

Document When to read it Size
HIG-LITE Every time you build UI — start here ~5 min read
Archetype pack After you know your page type — lists which topic guides to open ~2 min
Topic guides When your task needs detail — e.g. building a form, a combobox, or a data table ~3–10 min each
HIG.md Edge cases, disputes, or "what's the exact rule?" — the complete spec Reference only

Example: building a login form

  1. Page type = Auth / Account
  2. Read HIG-LITE for the basics
  3. Open the auth archetype pack — it tells you to load forms, security, and states guides
  4. Read rules/forms.md and rules/security.md for the details
  5. Only open full HIG.md if something isn't covered in the topic guides

Glossary

Terms you'll see in the docs — explained simply:

Archetype
A category of page (marketing, shop, app, login). Determines which rules are required.
Design token
A named design value (e.g. --color-primary) used instead of hard-coded colors or spacing.
HIG-LITE
The short "essential rules" document. Read this first for everyday work.
Rule ID
A code like HIG-A11Y-003 that identifies one specific rule. Useful in code review and AI prompts.
WCAG 2.2 AA
The international accessibility standard we target. Level AA is the practical compliance bar for most products.
Core Web Vitals
Google's metrics for load speed (LCP), interaction responsiveness (INP), and visual stability (CLS).
Container query
CSS that adapts a component to its container size — preferred over screen-width breakpoints for reusable components.
Progressive loading
Opening only the docs you need for the current task, instead of the entire specification every time.

FAQ

Do I have to follow every rule?

Follow the rules that apply to your page type and the feature you're building. Accessibility, tokens, performance, and security are always required. Use the archetype packs to see what's mandatory for your case.

Is this a component library?

No. It tells you how components and pages should behave. You implement them in your own framework (React, Vue, etc.). Framework-specific tips live in the framework/ folder.

I'm not using AI — is this still for me?

Yes. The HIG is written for human developers and designers first. The AI-related parts are optional extras for teams using Cursor, Copilot, or similar tools.

How is this different from a normal style guide?

A style guide covers look and feel. This also covers behavior: what happens when a form fails, how delete buttons should work, how fast the page should load, and how to meet accessibility law-level standards.

Can I change rules for my product?

You can document exceptions with justification. You cannot skip security, accessibility, or data-protection rules. See the Exception System in the full spec.

Using with AI tools

If you use Cursor, GitHub Copilot, or Claude Code, don't paste the entire HIG into every chat. It's too long and the AI may miss important details or invent its own rules.

Instead, teach your AI tool to:

  1. Always start with HIG-LITE
  2. Ask what page type the feature is (marketing, shop, app, login)
  3. Load the matching topic guide only when needed (forms, accessibility, etc.)
  4. Cite rule IDs (like HIG-A11Y-003) when explaining decisions

Copy-paste rule templates for your tool: examples/agent-rules/

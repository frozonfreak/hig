# Web HIG research brief — 2026-11-06

Sources checked on 6 November 2026. Coverage is 31 October–6 November 2026. Disposition for **v1.17.0**: declare supported color schemes before JavaScript and review Safari Adaptive Dark Mode visually; use Long Animation Frames style and layout durations as diagnostics only; keep HTML-in-Canvas informative. No new rule IDs.

| Safari Adaptive Dark Mode, Safari 27.3 beta, 3 November 2026 | [WebKit](https://webkit.org/blog/18541/introducing-adaptive-dark-mode/) can repaint a light page when the user enables Adaptive Dark Mode. `color-scheme: light dark` (meta or CSS on `:root` / `body`) prevents that repaint. `color-scheme: light only` is the documented opt-out, and the `only` keyword was not supported in beta 1. The transform can change CSS colors and gradients, some SVG and simple bitmap logos, and some masks or `mix-blend-mode` effects. Canvas content stays as drawn. Computed styles and other script-visible colors remain the authored values. WebKit aims for 4.5:1 text contrast after the transform. | **Change.** [§3.1](../../HIG.md#supported-color-schemes) and [tokens](../../rules/tokens.md) require the supported schemes in the initial document. `light only` is an opt-out, not the default. [§5.1](../../HIG.md#51-standards-baseline) measures authored contrast. The 4.5:1 aim is not WCAG conformance. [Fixture](../../examples/audit-fixtures/safari-27-3-adaptive-dark-mode.md) covers text, focus, hover, an SVG logo, a transparent bitmap, and canvas, on a declared page and an undeclared page. Screenshot review. Execution pending. |
| Long Animation Frames style and layout durations, Chrome 157 | [Chrome 157 release notes](https://chromestatus.com/release-notes/157) add style and layout timing. [Chrome’s INP guide](https://developer.chrome.com/docs/modern-web-guidance/guides/performance/identify-inp-causes) names `styleDuration` and `layoutDuration` on the frame, and `forcedStyleDuration` and `forcedLayoutDuration` on the script. High style time points at selectors, invalidation, and class or custom-property churn. High forced style time points at synchronous style reads such as `getComputedStyle()` after a write. High forced layout time points at geometry reads such as `getBoundingClientRect()` after a write. The same guide keeps `forcedStyleAndLayoutDuration` and the combined style-and-layout duration as the fallback. The fields are not in every major browser. | **Change.** [§6.2](../../HIG.md#long-animation-frame-diagnostics) and [performance](../../rules/performance.md) use the four fields when present and the combined timing otherwise. The release-note shorthand names `styleDuration` and `forcedStyleDuration`; the diagnostic split follows the INP guide, so forced layout reads are `forcedLayoutDuration`, not `forcedStyleDuration`. No new pass/fail. §6.1 and **HIG-PERF-001** are unchanged. |
| HTML-in-Canvas, Chrome 157 | [Chrome’s overview](https://developer.chrome.com/blog/html-in-canvas) ships the API after an origin trial. [WICG/html-in-canvas](https://github.com/WICG/html-in-canvas/) is the proposal. Drawn DOM can stay in the accessibility tree and can support selection, forms, find-in-page, translation, and indexing. Chrome documents feature detection and a fallback. One engine is not a general endorsement. | **Defer.** [§5.2](../../HIG.md#html-in-canvas-informative) keeps the semantic-DOM preference and lists the checks that would have to pass before an implementation qualifies. No audit rule until another engine implements it and independent assistive-technology testing exists. |

## Review rationale and compatibility

- **User harm:** A light page can be repainted in Safari while contrast tools still read the original colors, so focus, logos, and canvas charts fail on screen and pass in CI. Treating `light only` as the default opts people out of a dark appearance they asked for. Merging style and layout time hides which INP fix to try. Treating HTML-in-Canvas as generally accessible would bless a Chromium-only path before assistive-technology evidence exists. A Technology Preview fix is not yet something other Safari users have.
- **Capability condition:** Color-scheme guidance applies to pages that ship a light appearance, a dark appearance, or both. The screenshot applies when Safari is in the supported matrix. Long Animation Frame fields apply when the browser exposes them; otherwise the combined timing remains. HTML-in-Canvas guidance applies only where a product draws DOM into a canvas. The Technology Preview note applies to list markers, nested frames, and text zoom.
- **Evidence:** Primary sources are linked above. Safari screenshot execution and assistive-technology execution are pending. No measured contrast pass and no HTML-in-Canvas accessibility pass are claimed. Chrome’s four-field split is their current INP guide, not a cross-browser Baseline feature.
- **Alternatives:** Declare `light dark` and author both schemes. Omit Adaptive Dark Mode testing only when Safari is outside the matrix. Diagnose INP from the combined style-and-layout duration where the new fields are missing. Keep canvas tasks in the DOM. Wait for stable Safari before relying on the Technology Preview fixes.
- **Test cases:** Open the declared fixture with a dark system appearance and confirm Safari does not repaint authored colors. Open the undeclared fixture, enable Adaptive Dark Mode, and screenshot text, focus, hover, the SVG, the transparent bitmap, and the canvas. Compare computed color with the screenshot. Read a long-frame entry with and without the new fields and confirm the report does not gain a pass/fail. Feature-detect HTML-in-Canvas and confirm the non-supporting path still operates.
- **Exceptions:** No new stable-metric threshold. No WCAG pass inferred from Safari’s 4.5:1 aim. No reliance on `only` in Safari 27.3 beta 1. No HTML-in-Canvas audit rule. No change to compatibility expectations from Safari Technology Preview 256. No new AI or WCAG requirement.
- **Compatibility:** Backward-compatible clarification of **HIG-A11Y-002**, **HIG-A11Y-003**, **HIG-PERF-001**, and **HIG-PERF-002**, plus a new authoring MUST in §3.1 to declare supported schemes before JavaScript. No new IDs, severity changes, or Layer 0 changes. Quick remains 98 imperatives. The registry remains 76 stable IDs. `light only` is not a new default.

The separate audit site is not implemented or deployed by this repository change. Its dark-mode view should follow §3.1, and its performance view should follow §6.2. Fixture results must be recorded separately.
